# HF Drive — build, packaging, signing and installation

This document describes the implemented build/packaging/install pipeline for the
single multi-executable HF Drive MSIX. It records exact commands and the pinned
toolchain; where a step needs external identity or a separate machine, that is
stated as a named gate rather than implied to have passed.

Related documents: `docs/lifecycle.md` (install/upgrade/uninstall behavior),
`docs/verification.md` (gate policy), `packaging/AppxManifest.xml` (package
contract).

## Pinned toolchain

| Component | Pin | Source |
| --- | --- | --- |
| Rust | 1.99.1, `x86_64-pc-windows-msvc` | `rust-toolchain.toml` |
| Visual Studio Build Tools | 2026, 18.12 feature line (`18.12.12405.243`), x64 MSBuild | discovered by `scripts/Initialize-BuildEnvironment.ps1` (vswhere, BuildTools-only) |
| MSVC toolset | v145 `14.52.37025` | `Enter-VsDevShell -vcvars_ver=14.52.37025` |
| Windows SDK (native + packaging) | `10.0.28000.0` (servicing `10.0.28000.2957`) | MakeAppx/MakePri/SignTool from `Windows Kits\10\bin\10.0.28000.0\x64` |
| .NET SDK | `11.0.100` (roll-forward disabled) | `global.json` |
| .NET runtime (self-contained) | `11.0.0` | desktop project `PinDotNetRuntime` target |
| Windows App SDK (WinUI 3) | `2.6.5`, self-contained | `Directory.Packages.props` |
| Managed TFM / projection | `net11.0-windows10.0.26100.0`, `WindowsSdkPackageVersion 10.0.26100.87` | desktop project |

Runtime declarations in the manifest are separate from the build SDK:
`TargetDeviceFamily MinVersion="10.0.22621.0"` (Windows 11 22H2, the supported
minimum OS) and `MaxVersionTested="10.0.26100.0"`. The 28000 SDK is a build/packaging
tool, not a runtime or OS claim. There is no fallback to VS2022, an ambient MSBuild,
.NET 10, or an older Windows SDK; `Initialize-HfDriveBuildEnvironment` fails hard on
any mismatch.

## Fixed package identities

| Identity | Value |
| --- | --- |
| Package identity name | `HFDrive` |
| Development publisher | `CN=HFDrive Development` (must match the signing certificate Subject forever) |
| Production publisher | `$env:HFDRIVE_PACKAGE_PUBLISHER` (real certificate Subject) |
| Application IDs | `HFDrive` (desktop/tray), `Provider` (`provider\hfdrive-provider.exe`), `Cli` (`cli\hfdrive.exe`) |
| Startup task | `HFDrive.Provider`, **disabled by default** |
| CLI execution alias | `hfdrive.exe` (console, `uap5` classic alias) |
| Architecture | `x64` |
| State directory | `%LOCALAPPDATA%\HFDrive` — excluded from MSIX write virtualization (`virtualization:FileSystemWriteVirtualization`), physically survives package removal |

Package name, publisher, application IDs, provider GUID and root IDs must never
change after release.

## Package layout (one explicit multi-executable MSIX)

```
AppxManifest.xml
Resources.pri
HfDrive.Desktop.exe            + self-contained .NET 11 + Windows App SDK output
                                + release app-local v145 CRT (Microsoft.VC145.CRT)
provider\hfdrive-provider.exe  + release app-local v145 CRT
cli\hfdrive.exe                + release app-local v145 CRT
assets\StoreLogo.png, Square44x44Logo.png, Square150x150Logo.png,
       Wide310x150Logo.png, SplashScreen.png (+ .scale-* variants)
```

- Desktop publish is **self-contained** (`SelfContained=true`,
  `WindowsAppSDKSelfContained=true`, `RuntimeFrameworkVersion` scoped to
  `Microsoft.NETCore.App` = `11.0.0`); no NativeAOT, trimming or single-file.
- The **release** CRT from `VC\Redist\MSVC\14.52.37025\x64\Microsoft.VC145.CRT`
  is copied beside each executable group. Debug CRTs are refused.
- `scripts/package.ps1` refuses the run if the layout lacks `System.Private.CoreLib.dll`,
  `Microsoft.WinUI.dll`/`Microsoft.WindowsAppRuntime*.dll`, or the CRT files —
  there is no silent framework-dependent fallback. Any framework dependency
  packages found during publish are collected into `artifacts/package/Dependencies/x64`.
- `Resources.pri` is generated by the pinned SDK 28000 `MakePri` from the layout
  and manifest; the package is packed by `MakeAppx`.

The manifest template `packaging/AppxManifest.xml` contains exactly two tokens,
`{{HFDRIVE_PACKAGE_PUBLISHER}}` and `{{HFDRIVE_PACKAGE_VERSION}}`, rendered by
`scripts/package.ps1`. Assets are generated by
`packaging/assets/Generate-HfDriveAssets.ps1` (deterministic; re-runnable).

## Build

From a fresh PowerShell process at the repository root:

```
pwsh -NoProfile -File scripts/build.ps1 -Configuration Debug -Locked
pwsh -NoProfile -File scripts/build.ps1 -Configuration Release -Locked
```

`build.ps1` builds the Rust workspace with `cargo build --workspace --locked
--target x86_64-pc-windows-msvc` and the managed solution with the Build Tools
x64 MSBuild, then writes build provenance to `artifacts/build/`. It never mutates
machine/user PATH and never installs components.

The checked-in lockfiles are used on the first checkout too. `-InitializeLocks`
is only for intentional lockfile creation/updates, not a workaround for a failed
locked restore. The portable protocol library declares `win-x64` as an additional
restore target so solution builds and RID-specific desktop builds share the same
lockfile; its target framework remains `net11.0`.

Exit the desktop/tray UI before rebuilding. If the provider is running, stop it
explicitly using the existing Debug CLI:

```powershell
& .\target\x86_64-pc-windows-msvc\debug\hfdrive.exe provider exit --confirm
```

Closing the UI alone does not stop the provider. Windows cannot replace a running
`hfdrive-provider.exe`; graceful provider exit preserves work and registrations.
Do not delete state or regenerate lockfiles to work around that executable lock.


## Signing identity — explicit and fail-closed

Two separate, explicit user-authorized steps exist for development signing.
**Neither runs automatically, and no other script performs either action.**

### 1. Create the development certificate (certificate creation only)

```
pwsh -NoProfile -File scripts/New-HfDriveDevCertificate.ps1
```

Creates one self-signed code-signing certificate (`CN=HFDrive Development`,
non-exportable private key) in `CurrentUser\My` and exports the public
certificate to `artifacts\package\certs\HFDrive-Development.cer`. It refuses to
create a second certificate while one exists (ambiguous signing identity);
`-ReplaceThumbprint` removes a specific one first. This step does **not** trust
anything.

### 2. Trust the development certificate (separate security decision)

```
pwsh -NoProfile -File scripts/Install-HfDriveDevCertificateTrust.ps1 -ConfirmTrust
```

Imports the public certificate into `CurrentUser\Root` (or also
`LocalMachine\Root` with `-LocalMachine`, requiring elevation). It refuses to run
without `-ConfirmTrust`. A trusted root can sign any certificate: use this only
on development machines and remove the trust when done:

```
Remove-Item 'Cert:\CurrentUser\Root\<thumbprint>'
```

Production packages never use this certificate and never need trust steps; they
use a real certificate from a trusted authority.

## Package (sign + verify)

```
# Development-signed artifact (Release build):
pwsh -NoProfile -File scripts/package.ps1 -Configuration Release -Development -Version 0.1.0.0

# Production (real identity from the certificate store; fails closed if absent):
$env:HFDRIVE_PACKAGE_PUBLISHER    = 'CN=Your Company'      # exact cert Subject
$env:HFDRIVE_SIGN_CERT_THUMBPRINT = '<thumbprint>'          # Cert:\...\My
$env:HFDRIVE_TIMESTAMP_URL        = 'https://timestamp.digicert.com'
pwsh -NoProfile -File scripts/package.ps1 -Configuration Release -Production -Version 0.1.0.0
```

Exactly one of `-Development`/`-Production` is required; `-Production` requires
`Release`. `-Version` is four-part (`major.minor.patch.build`, parts 0..65535)
and its `major.minor.patch` must equal the desktop project's `<Version>`.

Validation and outputs (`artifacts/package/`):

- publisher ↔ certificate Subject compared by encoded X.500 bytes; expiry checked;
- `SignTool /fd SHA256` (+ `/tr <url> /td SHA256` and `verify /pa /tw /all` in
  production); development signatures are verified for presence/identity and
  their observed chain status is recorded honestly;
- `HFDrive_<version>_x64.msix` plus `<msix>.sha256` and
  `package-provenance-<version>.json` — toolchain paths/versions, signer identity,
  dependency inventory (self-contained .NET/Windows App SDK/CRT file versions),
  framework dependencies, checksums and explicit `not_run` external gates.

## Install (development)

```
pwsh -NoProfile -File scripts/install-dev.ps1 -Package artifacts/package/HFDrive_0.1.0.0_x64.msix
```

`install-dev.ps1` validates the package before `Add-AppxPackage` (identity,
publisher = development publisher, x64, the three application IDs, the
`hfdrive.exe` alias, `HFDrive.Provider` startup task disabled by default, the
state-directory exclusion) and refuses an unverified signature with the exact
trust command to run first. Same-version installs need `-Reinstall`; version
changes must go through `scripts/upgrade.ps1` (downgrades are refused). The
script never touches `%LOCALAPPDATA%\HFDrive` and writes an install record to
`artifacts/acceptance/install-dev-<version>.json`.

Activation (also printed by the script):

```
Start-Process "shell:AppsFolder\<package-family>!HFDrive"    # desktop/tray UI; starts Provider when needed
Start-Process "shell:AppsFolder\<package-family>!Provider"   # optional provider-only launch
hfdrive status --json                                        # CLI alias
```

On first launch, or when the provider reports no configured drives, the desktop
shows compact onboarding instead of the navigation shell. Configured users go
directly to the normal app; **Add drive** reopens the compact form. See
[Desktop onboarding](oauth-setup.md#desktop-onboarding) for the four-step flow.


## Static regression tests (no packaging/signing/install performed)

```
pwsh -NoProfile -File scripts/tests/Packaging.Tests.ps1
```

Validates the manifest contract, asset references, script parseability,
certificate-action containment (only the two dedicated scripts may create or
trust certificates) and strict version/identity helper behavior.

## External gates (not run)

| Gate | Requirement | Status |
| --- | --- | --- |
| Production signing | Real store certificate + `HFDRIVE_SIGN_CERT_THUMBPRINT`/`HFDRIVE_PACKAGE_PUBLISHER`/`HFDRIVE_TIMESTAMP_URL`; timestamped, verified package | `not_run` (credentials absent; fail-closed) |
| Development trust install | Explicit user-authorized trust step | `not_run` (never run by build/packaging; by design) |
| Clean-machine runtime check | Clean Windows x64 account/VM with **no** preinstalled .NET 11 / Windows App Runtime; launch desktop + provider + CLI, verify self-contained startup | `not_run` (requires a clean VM; developer-machine runtimes must not be treated as evidence) |
| Minimum OS (22H2) launch + CFAPI | Windows 11 22H2 acceptance VM (build 22621) | `not_run` (requires the acceptance VM) |
| MSIX install/uninstall/upgrade lifecycle | Real package store; see `docs/lifecycle.md` and `scripts/verify-lifecycle.ps1` | `not_run` (no package was built/installed in this slice; scripts are implemented) |

An MSIX package build/sign/install was **not** executed in this work slice
(assignment constraint). All packaging scripts are implemented and statically
checked; the first real package run must be the parent-verified
`build.ps1` → `package.ps1` → `install-dev.ps1` sequence above.
